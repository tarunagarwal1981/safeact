When an agent dies mid-run and retries, it re-fires the actions that already happened — the same email 40 times, the same card charged twice. Durable-execution engines persist an agent's state. They don't make its actions safe. safeact is one Python decorator that does — backed by a single SQLite file, no server.

The whole change

One decorator. A caller-supplied key. Done.

The side effect stays exactly as you wrote it. You add @safe and pass a key that names the logical action. Same key seen again → the stored result is returned instead of re-running. This holds across process restarts, because the record lives in SQLite, not memory.

    )

refund_agent.pyafter — at most once
from safeact import safe

@safe(store="agent.db")
def send_receipt(key, to, amount):
    email.send(
        to=to,
        subject="Your refund",
        body=f"Refunded ${amount}.",
    )
    return {"sent": True}

# key is the required first arg — impossible to forget
send_receipt("refund-8842", to, amount)
Anatomy of one safe call

Record before execute — so a crash is loud, not silent.

safeact commits ATTEMPTING to disk before the side effect runs. That committed marker is what turns a would-be duplicate into a detectable event. Step through a call — then crash it in the gap and watch it refuse to guess.

Two paths. Run normally reaches SUCCEEDED and stores the result. Crash in the gap kills the process after the effect fired but before the outcome was recorded — the one case we genuinely cannot resolve. The next call with that key raises InDoubtError instead of blindly retrying.
The honest limitation.  safeact does not pretend the gap between "effect ran" and "outcome recorded" doesn't exist — it's inherent to talking to a system outside your transaction. A key stuck there is marked in_doubt and surfaced to a human, never silently re-run. An honest in-doubt beats a confident duplicate.
Compensation

When step 3 fails, steps 2 and 1 undo themselves — in reverse, once each.

A Saga runs a sequence of @safe steps. If any step raises, it calls the compensators of everything already completed, in reverse order. Each compensator is itself idempotent — so a rollback that gets interrupted and replayed never double-refunds.

Four guarantees — each proven by a crash-test, not a mock

If a guarantee can't be crash-tested, we don't claim it.

Every property below ships with a pytest that fails if you remove the property. The tests double as the spec.

Idempotency

N retries, one execution

A counter-backed tool called N times with the same key executes exactly once — across process restarts, because the record is on disk.

test: 40 retries → counter == 1
Compensation

Reverse-order undo, once each

A failing Saga rolls back completed steps in reverse. Run the rollback twice and each compensator still fires exactly once.

test: 3-step saga, step 3 fails → 2,1 compensated once
Durable record

Written before it counts

Every attempt is committed to SQLite before the side effect is considered done, so recovery reads truth, not a guess.

test: reopen DB after crash → state is on disk
Honest in-doubt

Refuses to guess

Crash between execute and record → the key lands in in_doubt and the next call raises InDoubtError. No blind retry.

test: crash-in-gap → InDoubtError, counter still 1
Temporal · DBOS · durable execution

Persist and replay the agent's state — where it was in the workflow. Priceless for resuming. But on replay they happily re-run the code that talks to the outside world.

safeact

Guards the action itself. It's the last inch before email.send() or stripe.charge() — a layer you drop underneath any of them. One file, no infra, composable.
